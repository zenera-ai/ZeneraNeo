# Failure matrix and recovery decisions

## Failure scenarios

| Scenario                                                            | Observable signal                                                                                                             | Unsafe response                                               | Safe response                                                                                                                                | Human required?                                        |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| Package 3 publish fails after packages 1–2 succeeded                | Job exits non-zero; registry contains a prefix of the dependency-ordered package set                                          | Restart from package 1 and publish all again                  | Reconcile every exact `name@version`; verify existing versions and publish only confirmed missing versions                                   | No, unless a conflict is found                         |
| Publish request times out after registry acceptance                 | Client timeout; subsequent registry lookup may show the version                                                               | Blindly retry `npm publish`                                   | Query the exact version with bounded retries; if visible, verify; if still ambiguous, block                                                  | Only if ambiguity persists                             |
| Registry lookup returns 401/403/429/5xx/network error               | Non-404 error or transport failure                                                                                            | Treat every non-zero `npm view` as “not published”            | Classify response; stop on auth/throttle/server/network failure and preserve logs                                                            | Usually operator action for credentials/service outage |
| Two releases start together                                         | Multiple runs share release group or contend for lock                                                                         | Allow each to publish independently                           | Serialize via one repository-wide group/lock, validate tag+commit under lock, never cancel active publisher                                  | No                                                     |
| A third tag arrives while one run is active and one pending         | New run replaces the existing pending run under the default Actions queue setting                                             | Assume `cancel-in-progress: false` preserves every queued tag | Set `queue: max` (up to 100 pending runs) or use a durable release dispatcher; verify intended sequencing after lock acquisition             | No, unless queue capacity is exhausted                 |
| Existing `name@version` exists with unexpected metadata             | Registry version exists but integrity/metadata does not match expected build                                                  | Skip because version string exists                            | Mark `BLOCKED`; do not mutate immutable package; investigate and cut a corrected version if needed                                           | Yes                                                    |
| Tag is moved or same tag points to a different commit               | Tag object/peeled commit differs from manifest                                                                                | Continue because tag text matches                             | Stop before side effects; never move a consumed release tag                                                                                  | Yes                                                    |
| Docker image build fails after npm set is complete                  | npm job is green; one or both image jobs fail                                                                                 | Re-run the entire package publication without checking state  | Resume the image stage only; verify npm dependencies first; skip already verified image digests                                              | No, unless repeated build failure or artifact mismatch |
| Runner exits after publish but before manifest update               | Manifest still says `PUBLISHING`; registry contains version                                                                   | Trust stale manifest and publish again                        | Reconcile registry, verify exact artifact, then advance manifest                                                                             | No if exact state can be verified                      |
| GitHub Release creation fails after all packages publish            | Packages all verified; release metadata missing                                                                               | Republish packages                                            | Create or reconcile the GitHub Release entry for the same tag                                                                                | No                                                     |
| Retry follows a run that already created its GitHub Release         | Tag's GitHub Release entry already exists                                                                                     | Unconditionally call `gh release create` again                | Query the existing release, verify tag and target commit, and treat a matching entry as success                                              | No, unless metadata conflicts                          |
| Image wait passes but an internal transitive package is not visible | `npm view` succeeds for listed CLI/RAG packages, but Docker dependency install returns `ETARGET` for another internal package | Check only the matrix's top-level `needs` entries             | Wait for the full internal dependency closure required by the image, classify registry responses, and verify each exact version              | No, unless a mismatch persists                         |
| New workspace has no npm trusted publisher                          | `ENEEDAUTH` on that package; later packages never reached                                                                     | Keep retrying without bootstrapping trust                     | Follow documented one-time bootstrap: publish first version through approved operator path, configure trusted publisher, then retry same tag | Yes, one-time                                          |
| GHCR push succeeds but runner loses response                        | Image tag may exist; job status failed                                                                                        | Rebuild/push blindly                                          | Inspect manifest list, verify platforms and digest; mark verified if it matches                                                              | No if exact image can be verified                      |
| Published package is defective                                      | Consumers can resolve/install the bad immutable version                                                                       | Delete/rewrite tag or assume unpublish is safe                | Deprecate the version, publish a corrected patch, document impact; consider unpublish only under npm policy and maintainer approval          | Yes                                                    |

## Real repository evidence: v1.3.2 on 2026-11-13

GitHub Actions run: <https://github.com/zenera-ai/ZeneraNeo/actions/runs/43405142340>

The `publish` job completed successfully, including the npm publish loop and GitHub Release creation. Both matrix image jobs failed. The npm log shows `@zenera/server@1.3.2` was accepted by `npm publish` at 09:57:59 UTC, with npm warning that the package was still being processed and could take a few minutes to become available. At approximately 10:03 UTC, both Docker builds failed with `ETARGET` for that same internal package version. The image readiness checks in the workflow list only `@zenera/cli` for the agent runtime and `@zenera/cli` plus `@zenera/rag` for the sandbox; they do not explicitly wait for the full internal dependency closure. The evidence is consistent with a registry-visibility/readiness gap for a transitive dependency, although the logs alone do not prove the registry's internal propagation path.

This demonstrates the package-vs-image completion boundary: the npm publish job and GitHub Release succeeded; downstream image distribution did not. This run is not evidence of a partial npm package publish. Keep those classifications distinct in reports and incident communication. The repository also documents that local image builds remain available when prebuilt images are missing, so this should be recorded as degraded image-cache availability rather than an unpublished npm release.

## Evidence to record on every attempt

- Workflow run ID, attempt number, actor, trigger type, tag, and peeled commit SHA.
- Node and npm versions; lockfile SHA; package build artifact hashes.
- Registry request target, response class, elapsed time, and sanitized error output. Never log credentials or OIDC tokens.
- For each package: expected version, observed registry state, integrity, publication attempt count, and timestamps.
- For each image: tag, platforms, resulting digest, build run, and verification result.
- Manifest state transitions and operator decisions.
- Which internal package versions were checked before each image build, including transitive dependencies and registry response classes.
- Whether an existing GitHub Release entry was reused or created on this attempt.
