# Hostile archives

`zen import` unpacks an archive somebody else wrote. The exporter only emits
paths under one root, regular files, directories, and modes it chose itself;
an archive from anywhere else can claim something else entirely. This report
records what the importer did with eighteen archives it should refuse, and with
seven it should accept under a stated policy.

The archives are generated by a script and never committed. `results.json` is
the evidence; `results.md` is the same table without prose.

## Reproduce

```sh
npm run build
npm run hostile:archives
```

The runner lives in `scripts/hostile-archives.mjs`. It builds each archive under
`reports/hostile-archives/archives/` (ignored by git), runs the real
`packages/cli/dist/main.js --json import <archive> <landing> --no-register` in a
fresh home and landing directory, and records the exit code, the message, and
every file that landed. It exits non-zero if any case disagrees with its
expectation.

`--quick` builds small stand-ins for the two floods and the 64 MiB bomb, for a
fast check. The CLI cannot lower its own limits, so a quick run marks those
cases `not exercised` rather than pretending they passed. The report below is
from a full run.

The same catalogue backs the tests:

```sh
npm test -- packages/cli/test/archive.test.ts packages/cli/test/archive-hostile.test.ts
```

## What was tested

The production limits are 200,000 entries and 8 GiB unpacked
(`ARCHIVE_LIMITS` in `packages/cli/src/archive.ts`). Every case below uses those
limits; the tests shrink them only where the alternative is a fixture measured
in gigabytes.

No case wrote anything outside its landing directory, and every refusal left
the landing directory empty. The full run takes about ten seconds; most of that
is writing the 200,001-record floods.

## What was wrong

The pre-existing guards already refused path traversal, absolute paths,
backslashes, entries outside the manifest root, encrypted entries, and a
traversing manifest. `safePath` checks every segment and then resolves the
result under the target; yauzl also rejects `..`, absolute names and stored-size
lies while reading the central directory. Modes were already replaced, so
setuid and world-writable claims did not survive.

The audit found six gaps, all fixed in `packages/cli/src/archive.ts`:

1. **The guard ran while writing, not before it.** A benign entry before a
   hostile one was already on disk when the refusal happened, so `partial-write`
   left a partial project. `extractArchive` now calls `inspectArchive` first,
   which reads the central directory and touches nothing. The same checks run
   again while writing as a TOCTOU defence.
2. **Directory entries were skipped before their mode was checked.** A symlink
   with a trailing slash was treated as a directory and never examined. The
   shared `classify` checks encryption, type and name before deciding what the
   entry is.
3. **Only symlinks were refused among non-regular types.** A fifo, socket or
   device mode was written as a regular file. Any type other than a regular
   file or a directory is now refused.
4. **The entry bound counted files, not entries.** A flood of directory records
   passed because none of them was a file. The end-of-central-directory count is
   checked immediately, and every entry counts toward the bound thereafter.
5. **Collisions were resolved by extraction order.** Duplicate paths, case-only
   differences, NFC/NFD spellings and file/directory conflicts either silently
   overwrote one entry or failed halfway with `ENOTDIR`. `PathClaims` folds
   names with NFC and lowercasing and refuses all four before writing.
6. **Reader errors escaped as plain `Error`.** yauzl's own refusals produced exit
   1 and no useful sentence. `archiveError` maps them to the invalid exit code
   (3) with the archive named.

`readManifest` also gained the entry-count bound and an encrypted-manifest
check, so an absurd archive is refused before the manifest is even read.

The bounds are now injectable through `ExtractOptions.limits` so the tests can
build a six-entry "flood" and a 1 MiB "bomb". The CLI always uses
`ARCHIVE_LIMITS`; nothing in production can lower them.

## Residual risk

These are known and deliberately not fixed in this change.

- **A compressible payload below 8 GiB is accepted.** The defence is an absolute
  byte bound, not a compression-ratio rule. `bomb-under-limit` is the proof: a
  small archive writes 64 MiB, and the same shape can write almost 8 GiB before
  the bound refuses it. A ratio guard needs a policy for legitimate highly
  compressible files, so it is left for a separate decision.
- **Extraction is not atomic.** Preflight means every refusal based on what the
  archive _claims_ happens before the first write. An I/O failure after that
  point (disk full, permission denied, `ENAMETOOLONG`) can still leave a partial
  tree, and an existing target file can be overwritten with no rollback.
  Staging into a temporary directory and renaming would fix this; it is out of
  scope here.
- **The target's own filesystem is not resolved.** `safePath` is textual. A
  pre-existing symlinked directory inside the landing directory is followed by
  `mkdir` and `createWriteStream`, so a caller that imports into a directory it
  does not control can still be redirected outside it. Importing into a fresh
  directory, as `zen import` normally does, avoids this.
- **The archive can change between the two passes.** Per-entry checks catch a
  different name, type or size, but not different bytes under the same claims.
  There is no signature or content hash to compare against.
- **Case folding is NFC plus lowercasing, not full Unicode case folding.**
  Exotic folds (for example German `ß` against `SS`) can still collide on a
  filesystem that folds them more aggressively. No common project name is
  affected.
- **Names Windows cannot represent are accepted on Linux.** `CON`, `aux.txt`,
  `name.` and `C:/x` are valid on Linux and were imported. A later Windows
  checkout has to deal with them. Refusing them everywhere would reject names
  Linux users can legitimately have, so the report records the difference
  rather than hiding it.
- **Empty directory entries do not travel.** The importer creates directories
  from the files it writes, so an archive with only `proj/empty/` is accepted
  and materialises nothing. This matches the exporter, which does not preserve
  empty directories either.
